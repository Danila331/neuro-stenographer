### Выводы архитектора

- **Q2 главнее Q1:** для автоматической проверки модели **должны быть встроены в APK**. Загрузка из
  сети — только дополнительная функция для UX, без неё основная задача обязана работать.
- **Проверка автоматическая** → путь «импорт → обработка → экспорт JSON» должен проходить без
  ручных шагов и диалогов: без экранов первого запуска, без обязательных разрешений, без выбора
  модели. Нужно уточнить у организаторов, как именно автоматизируют (UI-скрипт, intent, adb).
- **Q3:** тестовые записи могут быть сделаны на диктофон на встрече: дальнее поле, эхо
  помещения, разная громкость участников, фоновый шум.
- **Q4:** потребление RAM/CPU не оценивается → оптимизацию памяти делаем только ради отсутствия
  падений (OOM) и скорости; замеры пиковой RAM и нагрузки показываем на защите.
- **Q5:** нужны оба сценария: быстрые разговорные звонки (перебивания, сжатое «телефонное» аудио)
  и встречи в умеренном темпе (дальний микрофон, Q3).
- **Q6:** только arm64-v8a — верно. Проверка, вероятно, на **ARM-эмуляторе**: мало RAM (часто
  2–4 ГБ), 2–4 ядра, нет GPU/NPU. Значит, основной сдаваемый APK обязан работать и укладываться
  по времени на стандартном ARM-эмуляторе; GPU-ускорение — только с откатом на CPU.
- **Q7:** русский — главный (на нём WER и подбор моделей), но английская запись не должна давать
  мусор: нужно определение языка и английская ASR-модель хотя бы в основном APK.
- **Q8:** целевое устройство — 4 ГБ RAM, ARM. Приложению реально доступно ~1.5–2 ГБ → бюджет
  пиковой памяти сдаваемого APK ≤ 1.5 ГБ; модели грузятся по очереди (ASR/диаризация выгружаются
  до запуска LLM). Вариант hard (LLM 4B) на 4 ГБ не помещается — он только для флагманов и
  на автопроверку не идёт.
- **Q9–Q10:** автопроверка — чёрный ящик, и она **отсеивает до защиты** («в случае допуска к
  защите», Q12). Значит, главное — строго выполнить ТЗ и закреп: встроенная модель, импорт аудио
  из памяти устройства, обработка, экспорт JSON в файл. Как именно нажимают кнопки, мы не узнаем,
  поэтому поддерживаем все разумные способы входа и выхода (B3) и не добавляем ни одного лишнего
  шага (B2). Дозагрузка моделей автоматикой не учитывается — только UX на защите.
- **Q11:** LLM не обязана стоять в основном пути. Свобода выбора подтверждена: пунктуация
  специализированной моделью, LLM — протокол и вопросы (B18). LLM в APK оставляем: в ТЗ она
  названа обязательной, и это наш аргумент на защите.
- **Q12:** лендинг — только после всего остального, для защиты.
- **Q13–Q14:** пунктуация, по всей видимости, **входит в WER**, а ставится она по **интонации и паузам
  говорящего**, а не по правилам орфографии. Без пунктуации наш «сырой» WER ≈ 29 % при 3 % без
  учёта знаков — то есть пунктуация может стать главным резервом баллов. Предпочтение — моделям,
  которые слышат аудио (GigaAM v3 e2e с пунктуацией) и паузам из пословных меток; текстовые
  модели (RUPunct, LLM) ставят знаки «по правилам» и могут проигрывать. Буквы е/ё уравниваем.
